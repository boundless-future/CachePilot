# 3C 性能消融实施清单

长 pending 前缀拆分的正确性已通过，下一步检验保护是否减少重算，以及额外搬运和 pin 是否抵消收益。现有 `protection_zero_smoke.py` 开启逐步审计及 KV 内容检查，不得将它的耗时作为性能结果。

## 下一轮入口改造

1. 独立性能入口复用服务生命周期、固定 trace 和 ProtectionConnector 配置；提供 correctness 与 measurement 两种模式。measurement 关闭逐层 KV 拷贝和逐步 JSONL，保留运行终态检查、必要汇总计数及版本快照。
2. 客户端改为流式响应，记录计划到达、实际发出、首 token 和完成时间。HTTP 总耗时不代替 TTFT；封闭环/开放环分开标注。
3. 同一所有权适配栈、相同模型/资源/输入上比较预算 0、1、2 chunk；新增拆分后，旧“512-token 整项超预算拒绝”仅为历史结论，需要按当前前缀保护语义重新建立对照。
4. 每组先验收 payload 与生成 token 数，再在隔离实例中进行至少三轮交错顺序重复。不能复用前组 CPU/GPU cache；warmup 单独标记。

## 第一组矩阵与门槛

先固定 Qwen3-4B BF16、4090 24GB、eager、TP=1、2 GiB GPU KV、相同 CPU KV 容量。使用一个已验证可产生保护与 H2D 回载的固定压力 trace，先做三个预算各三次，再扫描 KV 容量和复用间隔。初轮不混入 raw-ID/延迟/故障诊断。

报告 TTFT P50/P95、实际 prefill token、排队时间（若无可用独立测量则明确缺失）、H2D/D2H 字节、STORE 数、保护/在途峰值、回退次数、策略 CPU 时间及运行期资源终态。并列列出零收益与退化；没有可测量收益也完成这一轮验证，不再以补充正确性专项无限推迟结论。

继续单列空闲延迟收尾和真实 driver/DMA fault 等限制；本组结论只适用于已验收的隔离服务范围。
