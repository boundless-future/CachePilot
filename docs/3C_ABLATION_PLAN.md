# 3C 性能消融实施清单

长 pending 前缀拆分的正确性已通过，独立性能入口已完成零、一、两 chunk 各三次正式重复。现有 `protection_zero_smoke.py` 开启逐步审计及 KV 内容检查，不得将它的耗时作为性能结果。

## 下一轮入口改造

1. 独立性能入口复用服务生命周期、固定 trace 和 ProtectionConnector 配置；提供 correctness 与 measurement 两种模式。measurement 关闭逐层 KV 拷贝和逐步 JSONL，保留运行终态检查、必要汇总计数及版本快照。
2. 客户端改为流式响应，记录计划到达、实际发出、首 token 和完成时间。HTTP 总耗时不代替 TTFT；封闭环/开放环分开标注。
3. 同一所有权适配栈、相同模型/资源/输入上比较预算 0、1、2 chunk；新增拆分后，旧“512-token 整项超预算拒绝”仅为历史结论，需要按当前前缀保护语义重新建立对照。
4. 每组先验收 payload 与生成 token 数，再在隔离实例中进行至少三轮交错顺序重复。不能复用前组 CPU/GPU cache；warmup 单独标记。

## 第一组矩阵与门槛

先固定 Qwen3-4B BF16、4090 24GB、eager、TP=1、2 GiB GPU KV、相同 CPU KV 容量。使用一个已验证可产生保护与 H2D 回载的固定压力 trace，完成三个预算各三次，随后扫描 KV 容量和复用间隔。2026-10-11 的 12 会话、1,024-token pilot 只有 D2H 而没有 H2D；16/13 会话的单阶段压力虽有 H2D，却让所有非零预算候选走物理容量回退。这些均作为校准结果保留。正式初轮使用固定两阶段 trace：12 个可复用会话先在中等压力下产生 STORE，8 个独立压力会话随后驱逐，最后固定回访原会话触发 H2D。初轮不混入 raw-ID/延迟/故障诊断。

报告 TTFT P50/P95、实际 prefill token、排队时间（若无可用独立测量则明确缺失）、H2D/D2H 字节、STORE 数、保护/在途峰值、回退次数、策略 CPU 时间及运行期资源终态。并列列出零收益与退化；没有可测量收益也完成这一轮验证，不再以补充正确性专项无限推迟结论。

正式 9 cell 全部通过严格资源、日志、H2D、token 与保护 commit 门槛。one chunk 的 TTFT P95 均值相对 zero 低 6.22%，two chunk 低 3.45%；对应回访 TTFT P95 为 -4.33% 和 -1.48%。不将三次重复视为统计显著性，也不将 D2H 下降视为因果证明。完整原始结果、输出哈希差异和限制见 [正式报告](experiments/2026-10-11/PROTECTION_ABLATION.md)。

继续单列空闲延迟收尾和真实 driver/DMA fault 等限制；本组结论只适用于已验收的隔离服务范围。下一轮使用独立验证 trace，扩大 KV 容量和模型/硬件，而不是在同一 trace 上继续调参。
